# 集群概览（Cluster Overview）深度产品设计

> 状态：设计稿 v2，未实施。**本文修正了 v1 的错误结论**——v1 认为"概览不缺判定，只缺展示"，核实后不成立：判定层存在真实漏报。
> 前置阅读：`docs/design-system/MASTER.md`、`docs/design-system/pages/load-management-design.md`（闭环方法论来源）。
> 全部现状描述基于 `backend/src/services/overview_service.rs`、`metrics_collector_service.rs`、`cluster-overview.component.*`、`node.service.ts` 的真实代码。

---

## 1. 概览要回答的三个问题

1. **哪个集群在出事**（已经出事）
2. **哪个集群在变坏**（还没出事，但趋势不好）
3. **现在需要我做什么，去哪做**

v1 只覆盖了 1 和 3，漏掉了 2；并且第 1 条的**判定本身有漏报**，比展示问题严重得多。

---

## 2. 现状盘点（逐项核实，含证据）

### 2.1 已经做对的

| 能力 | 说明 | 证据 |
|---|---|---|
| 健康分 | 0-100 分 + 最严重级别，五维度扣分（计算节点离线、FE 离线、Compaction、磁盘、CPU） | `HealthAccumulator::record(...)` 调用点 |
| 状态与分数同源 | 同一份声明同时决定 `status` 与扣分，注释记录了历史上"横幅 Critical / 状态卡 Warning"的口径 bug | `HealthStatus::rank` + `HealthAccumulator` |
| 磁盘语义分支 | shared-nothing = 容量风险；shared-data = Data Cache 配额，写满是 LRU 稳态，**不误报** | `DiskMetricKind::from_cluster` |
| 告警条目 | 8 类：采集缺失、计算节点离线、Compaction 过高/偏高、容量、CPU、FE Safe Mode、Meta Log 未 Checkpoint、Meta Log 堆积 | `generate_alerts` |
| 告警建议动作 | 后端每条告警的 `action` 都填了内容，例如"检查计算节点状态并重启"、"清理过期数据或扩容磁盘"、"检查慢查询，优化查询性能" | `Alert { level, category, message, timestamp, action }` |
| 状态卡跳转 | 前端 `cardId` / `navigateTo` 映射到节点管理、审计日志等 | `overview.service.ts` `transformToHealthCards` |

### 2.2 真实缺陷（v1 漏判的部分）

**缺陷 A：磁盘判定用加权平均，会漏报"节点要写满"。**

```rust
fn cluster_disk_usage(samples: &[(f64, i64, i64)]) -> (f64, i64, i64) {
    let disk_total_bytes = samples.iter().map(|s| s.1).sum();
    let disk_used_bytes  = samples.iter().map(|s| s.2).sum();
    let disk_usage_pct = disk_used_bytes / disk_total_bytes * 100.0;  // 全集群加权平均
}
```

该行为被测试刻意固定：`cluster_disk_usage_is_weighted_not_hottest_node()`——是深思熟虑的选择，不是疏忽。

后果举例：10 台 BE、每台 10TB，其中 1 台写到 95%（9.5TB），其余 9 台各 50%（45TB）→ 平均 54.5% → **不告警**，而那台随时写入失败。

**缺陷 B：`max_disk_usage_pct` 采集了却没有任何判定使用。**

- 列已存在：`metrics_snapshots.max_disk_usage_pct`（`00000000_initial_schema.sql:273`）
- 采集已写入：`MAX(disk_usage_pct) as max_disk_usage_pct` + 插入绑定
- 判定零引用：`overview_service.rs` 与 `agent_runtime/` 均无引用

**缺陷 C：CPU 只有平均值，没有最大值。** 单节点 CPU 打满同样不告警，且连数据都没采（需加列迁移）。

**缺陷 D：告警不带具体对象。** "2 个计算节点离线"只有数量，跳到节点管理仍要人工找是哪两个。

**缺陷 E：没有"在变坏"。** 快照表有完整历史（`metrics_snapshots` 按 `collected_at` 保存），但没有任何趋势信号。磁盘 88% 且一周内从 60% 涨上来，与 88% 三个月不动，是完全不同的行动信号。

## 3. 核心设计决策

### 3.1 容量不足 ≠ 数据倾斜，必须分开判、分开处置

| 现象 | 结论 | 处置方向 | 产品现状 |
|---|---|---|---|
| 加权平均高 | 整体容量不够 | 扩容 / 清理冷数据 | 已有告警，处置靠人工 |
| 单节点高、平均正常 | 数据分布不均 | 检查分区分桶、清理该节点数据、扩容该节点磁盘 | **无告警**（缺陷 A） |
| 两者都高 | 既倾斜又不够 | 先扩容，再调分布 | 只有平均值告警 |

只报平均会漏掉倾斜；只报最大值会对"均匀但都满"的集群反复误报。**两条都要判，且归属不同的 category 与处置路径。**

诚实声明：**平台当前没有 rebalance 能力**（节点管理只能看 `MaxDiskUsedPct`，没有一键迁移 tablet 的操作）。所以倾斜类告警的处置路径是"跳节点管理定位 + 人工处理"，不设计一个不存在的按钮。

### 3.2 概览是分诊台，不是手术室

- 概览负责：把需要人管的挑出来、说清是什么、指到能处理的地方；
- 处置发生在节点管理、查询管理、参数配置、导入管理各自页面；
- **跨集群页面上不提供任何处置动作**——否则容易改错集群，也绕开各页面已有的权限与审计。

### 3.3 沿用的底线

- 只把能确定性判定的列为异常；趋势只能提示，不能断言因果；
- 拿不到的数据不画、不猜（缺数据时明确显示"暂无采集数据"，已有行为）；
- **不改变现有判定口径**（`status` 与 `score` 同源、磁盘按部署模式分支），新增维度不得与之冲突。

## 4. P0：补判定缺口（正确性问题，优先于一切展示工作）

### 4.1 单节点磁盘判定（零迁移，数据已就绪）

新增一条**独立**告警，与现有"容量"告警并列：

| 判定 | 条件 | 级别 | category | 文案示例 |
|---|---|---|---|---|
| 节点磁盘告急 | `max_disk_usage_pct > DISK_CRITICAL_PCT` | Critical | 节点分布 | `有 1 个节点磁盘使用率 95.2%（全集群平均 54.5%）` |
| 节点磁盘偏高 | `max_disk_usage_pct > DISK_WARNING_PCT` | Warning | 节点分布 | `有节点磁盘使用率 88.1%（全集群平均 61.0%）` |
| 整体容量不足 | 现有 `disk_usage_pct` 逻辑不变 | 维持现状 | 容量 | 维持现状 |

要点：

- **两个数并列展示**（最高节点 + 全集群平均），让用户自己看出是倾斜还是整体紧张，判断依据不被隐藏；
- 沿用现有 `DISK_WARNING_PCT` / `DISK_CRITICAL_PCT` 常量，不新增阈值；
- **shared-data 集群不生成该告警**（Data Cache 写满是 LRU 稳态，与 `DiskMetricKind` 现有语义一致）；
- 是否"倾斜"不在文案里下结论，只把两个数摆出来（避免误判单节点大盘 vs 倾斜）。

### 4.2 单节点 CPU 判定（需一条加列迁移，可选）

- 采集侧新增 `max_cpu_usage`（磁盘已有 max，CPU 没有）；
- 判定与文案同 4.1 的结构；
- **建议排在磁盘之后**：磁盘写满是不可逆硬故障，CPU 打满是可恢复软故障。

需要迁移：`metrics_snapshots` 加列，三方言（sqlite / mysql / postgres）。

### 4.3 P0 验收标准

- 构造"1 台节点 95% + 其余 50%"的数据，必须产生"节点分布"告警，且文案同时给出两个数值；
- 构造"所有节点均匀 85%"的数据，必须产生"容量"告警、**不产生**"节点分布"告警；
- shared-data 集群两种数据都不产生磁盘类告警；
- 现有健康分与告警口径不变（回归测试）。

## 5. P1：可操作性（有了正确判定之后，让用户能直接动手）

### 5.1 告警显示建议动作

告警条由「类别 + 消息」变为「类别 + 消息 + **该怎么处理**」，直接使用后端已有的 `action`。文案保持后端原文，前端不改写。`action` 为空（如"采集"类）时不占位。

### 5.2 告警带具体对象

- 节点离线：除数量外给出**节点名/IP 列表**（后端需从节点数据补取，节点信息已有）；
- 容量/分布：给出最高节点名与数值；
- 其余类别按同样原则：**能定位到具体对象就必须定位**，不允许只给一句概括让用户自己去找。

### 5.3 告警可点击跳转（沿用状态卡机制，前端映射）

| 告警 category | 跳转目标 | 依据 |
|---|---|---|
| 节点状态 | `/pages/starrocks/backends`（BE）/ `/pages/starrocks/frontends`（FE） | 按类别分派 |
| **节点分布** | `/pages/starrocks/backends` | 该页有 `MaxDiskUsedPct`，可直接定位最满节点 |
| 容量 / 资源 | `/pages/starrocks/backends` | 磁盘与 CPU 均在节点页可见 |
| Compaction | compaction 详情页 | 现有页面 |
| FE | `/pages/starrocks/frontends` | Safe Mode / Meta Log 在 FE 页 |
| 采集 | 无跳转 | 平台自身问题，提示即可 |

**没有对应处置页的告警不给箭头**——宁可不跳，不做假动作。

### 5.4 告警排序

按「级别（Critical 优先）→ 影响面」排序；同 category 的多条合并为一条（避免同类刷屏）。现有健康分的 `worst` 已按严重度取值，排序应复用它，不再引入第二套口径。

### 5.5 P1 验收标准

- 每条有 `action` 的告警都能看到"该怎么处理"；
- 可处置的告警能点进相关页面，且落地页与该告警相关；
- 节点离线告警能看到具体节点标识；
- 不改变任何判定口径与阈值。

## 6. P2：把"在变坏"变成信号

### 6.1 设计

基于既有 `metrics_snapshots` 历史（采集间隔 30s、保留 7 天，均为现有配置）计算趋势：

- **同环比**：与 1 小时前 / 24 小时前的同一指标比较；
- **持续时长**：某维度连续越界多久（区分"刚发生"和"挂了半天"）；
- 呈现形式为告警的附加信息，例如 `磁盘使用率 88.1%（24 小时内 +28.3%）`。

### 6.2 边界

- 只对**已有确定性判定的维度**做趋势附加，不新增维度；
- 趋势只作提示，不改变告警级别（避免"趋势判断"引入误报）；
- 保留期只有 7 天（现有配置），所以"一周内从 60% 涨到 88%"需要至少 7 天数据——不足时如实显示"数据不足"。

### 6.3 处置标记

用户可对某条告警点"我来处理"，写入 `op_audit_logs`（`target_type = "overview_alert"`，复用现有审计，不新建表）。只做"有人在处理"，**不做"已读/忽略"**——那会掩盖问题。

---

## 7. P3：跨集群视图

- 一行一个集群：集群名 + 健康分 + 最严重级别 + 异常条数 + 最严重一条的摘要；
- 按严重度排序，点进去落到该集群概览（复用 P1）；
- **只汇总与下钻，不做处置动作**；
- 数据源是各集群最近一次快照，不实时聚合（避免一屏打爆 FE）；
- 权限沿用组织隔离。

**推迟条件**：若当前客户均为单集群，本期可无限期推迟。

---

## 8. 明确不做（YAGNI）

- 不做自定义告警规则编辑器：先跑现有 8 类 + P0 新增的磁盘/分布类，缺哪类补哪类；
- 不做告警通知渠道：归平台级通知设计；
- 不做图表重构：现有趋势图与排行满足"看趋势"，P0-P3 不动它们；
- **不做 rebalance 操作**：平台没有该能力，也不在本文档范围内先造一个；分布倾斜只做"发现 + 定位 + 人工处置"；
- 不在跨集群页面提供处置动作。

## 9. 分期与优先级依据

| 期 | 内容 | 成本 | 出口 |
|---|---|---|---|
| **P0** | 单节点磁盘判定（容量 / 分布分离）；可选：单节点 CPU（需迁移） | 后端判定 + 文案，零迁移（磁盘部分） | 不再漏报"节点要写满" |
| **P1** | 告警显示 `action`、带具体对象、可跳转、按级别排序 | 前端为主 + 后端补对象信息 | 看到告警就知道是什么、去哪做 |
| **P2** | 趋势（同环比 / 持续时长）+ 处置标记 | 后端一个历史聚合查询 | 能区分"刚发生"与"挂了半天" |
| **P3** | 跨集群汇总 + 下钻 | 新端点（读各集群最新快照） | 多集群不再逐个切换 |

排序依据是"**正确性 > 可操作性 > 判断依据 > 规模扩展**"：判定漏报会让平台在节点要炸时说"一切正常"，这比任何展示问题都严重。

---

## 10. 与其它模块的关系

概览在这个平台里的价值是**分诊台**：把需要人管的挑出来、指到该去的地方、处置完能回来看是否恢复。真正的处置发生在节点管理、查询管理、参数配置、导入管理各自的页面，那些页面已有权限与审计约束。

这条边界被打破（把所有处置按钮塞进概览）会带来两个后果：页面迅速变成大杂烩；处置动作绕过各页面的权限与审计。因此在 P1-P3 中，概览只提供**发现与导航**，唯一例外是 P2 的"我来处理"标记——它是协作信号，不是处置动作。
