# Stellar Schema Explorer 与对象影响分析设计

> 状态：阶段 A 已交付；阶段 B 已交付 MV 一跳上游依赖，通用下游与快照差异仍待验证
> 范围：StarRocks / Apache Doris 已接入集群的只读对象认知、依赖证据与变更影响分析

## 1. 决策

Stellar 不集成 DrawDB，也不开发通用数据库设计器。Stellar 应提供以集群实时元数据为事实来源的 **Schema Explorer**，逐步补齐对象依赖和 DDL 影响分析。

DrawDB 解决的是“准备建成什么样的库表”；Stellar 解决的是“已接管的集群里有什么、谁依赖它、改动会影响什么”。两类产品都可展示表和连线，但数据来源、用户任务和正确性要求不同。

### 当前实施边界（2026-09）

| 范围 | 当前状态 | 保留边界 |
| --- | --- | --- |
| 阶段 A：对象详情 | 已交付 | 使用服务端签发的对象引用，字段、注释、DDL 与读取时间来自同一次受控读取。 |
| 阶段 B：MV 上游依赖 | 已交付 | 仅一跳直接读取；StarRocks 使用 `sys.object_dependencies`，Doris 仅返回显式标记为 `partial` 的定义提取结果。 |
| 阶段 B：通用下游地图 | 未交付 | 未验证的反向关系、权限拒绝或读取超时均不能显示为“无依赖”。 |
| 阶段 C：DDL 快照与差异 | 未交付 | 需要真实变更审查需求和可验证的持久化、保留策略后再立项。 |

物化视图页的依赖图不是自由编辑画布。它只表示当前选中 MV 的直接 `mv_reads` 证据，并呈现来源、采集时间、完整性与警告。

首期不新增顶层菜单。它应从 SQL 工作台的 Catalog / Database / Table 树进入，替代当前仅显示 `SHOW CREATE TABLE` 文本的表结构查看体验。后续的关系图必须服务于对象依赖和变更判断，而不是成为可自由编辑的画布。

## 2. 背景与问题

Stellar 已覆盖集群、节点、实时查询、Query Profile、物化视图、权限与操作审计。SQL 工作台能够列出 Catalog、数据库与表，并按需执行 `SHOW CREATE TABLE`。这解决了“能否拿到 DDL”，但没有解决以下日常问题：

1. 接管陌生集群时，用户无法快速确认一个对象的字段、键模型、分区、分桶、引擎和属性。
2. 写 SQL 时，用户需要找到正确的对象并确认可用字段，而不是只看到表名。
3. 修改表或物化视图前，用户需要知道已验证的上下游对象和可解释的影响范围。
4. StarRocks / Doris 的物理特征容易在通用 ERD 中丢失，例如分区、分桶、Key Model、`PROPERTIES`、外表和 Rollup。

自由编辑图无法解决上述问题：它需要人工持续维护，容易与真实 DDL 漂移，并可能让用户把主观关系误判为引擎事实。

## 3. 用户与待完成任务

| 角色 | 触发场景 | 用户问题 | 首选产品能力 |
| --- | --- | --- | --- |
| DBA / 运维工程师 | 接管或排查陌生集群 | “这个对象的真实结构和存储特征是什么？” | 对象详情、原始 DDL、物理属性 |
| 数仓工程师 | 修改基表、View 或 MV 前 | “谁引用它？这次变更可能影响什么？” | 依赖证据、DDL 差异、影响清单 |
| 数据分析师 | 编写或阅读 SQL | “应该使用哪张表、哪个字段？” | 对象搜索、字段列表、注释、SQL 工作台联动 |
| 平台管理员 | 审核受控变更 | “此变更是否基于最新集群状态？” | 带时间戳的快照、变更前后差异、审计 |
| 数据架构师 | 从零设计业务模型 | “新系统应该有哪些实体和关系？” | 不属于 Stellar 首期范围，使用独立建模工具 |

Query Profile、节点故障、磁盘倾斜和导入积压的主诊断面仍是指标、执行计划和运行时证据。Schema Explorer 可以作为上下文入口，但不能替代现有诊断功能。

## 4. 产品范围

### 4.1 应做

Stellar 的结构能力应稳定回答五个问题：

1. 对象在哪里：集群、Catalog、Database、表、视图、物化视图。
2. 对象长什么样：字段、类型、注释、键模型、分区、分桶、引擎、属性和原始 DDL。
3. 谁依赖它：有来源证据的 View / MV 定义、引擎声明约束和后续支持的人工审核注释。
4. 改动会影响什么：同一对象的 DDL 快照差异、已验证下游对象和关联的受控变更。
5. 信息从何而来：读取时间、集群、对象标识、DDL 原文、解析状态和关系证据。

### 4.2 明确不做

首期及已规划阶段均不做：

- 拖拽创建表、字段或任意连线。
- 通用 MySQL、PostgreSQL、SQLite 等多数据库设计器。
- 从图自动生成、自动执行或自动回滚 DDL。
- 根据字段同名、LLM 推测或历史 SQL 共现自动声明表关系。
- DrawDB 文件、模板市场、在线图纸协作或自由图版本管理。
- 将全量 DDL、对象关系或集群凭据发送给第三方服务或 LLM。

这些能力会将 Stellar 从运维控制平面扩展成独立的数据建模产品，且不能提高当前运行时运维闭环的可信度。

## 5. 产品原则

### 5.1 集群状态优先

对象详情、关系和差异以服务端从已授权集群读取的元数据为准。前端不得直接连接集群，也不得持有数据库凭据。

### 5.2 关系必须可解释

每条边都必须显示类型、证据来源、采集时间和解析状态。没有足够证据时不画线，并明确显示“未发现可验证依赖”，不能用空白图暗示对象没有关联。

### 5.3 原始 DDL 是回退真相

解析器无法理解的 StarRocks / Doris 方言不得被静默删除或转换。界面必须保留原始 DDL，并将解析失败或部分解析标识为状态，不输出猜测后的结构。

### 5.4 先局部、后全局

用户多数时候需要理解一个对象及其一跳上下游。首期不渲染全库大图；局部图限制节点和边数量，避免大库加载缓慢且不可读。

### 5.5 一份元数据，多个工作流复用

智能问数已经规划 MetadataSyncService 以同步 Catalog、库、表、字段、DDL、MV 与统计信息。本设计复用同一事实来源；不得另建只为关系图服务的元数据同步链路。

## 6. 术语与可信度

### 6.1 对象标识

对象的规范身份是：

```text
cluster_id + catalog + database + object_name + object_kind
```

其中 `object_kind` 至少包括 `table`、`view`、`materialized_view` 与 `external_table`。展示名称不得替代规范身份，避免同名对象在不同 Catalog 或数据库中混淆。

HTTP API 使用由服务端签发、URL-safe 的不透明 `object_ref` 表示该身份；它不是将 Catalog、Database、对象名或 SQL 片段直接拼入路由后的替代品。

### 6.2 关系类型

| 关系 | 含义 | 可作为首期图边 |
| --- | --- | --- |
| `view_reads` | View 定义引用上游对象 | 是 |
| `mv_reads` | 物化视图定义引用上游对象 | 是 |
| `declared_constraint` | 引擎明确返回的约束 | 是，前提是引擎和版本可验证 |
| `manual_annotation` | 用户提交并审核的业务关系 | 后续能力，不在首期 |
| `query_observed` | 历史 SQL 曾读取某对象 | 不作为结构关系，仅可在后续影响证据中展示 |

“ERD 关系”和“数据血缘”不是同义词。前者描述结构或业务实体关系，后者描述对象定义或 SQL 的读取依赖。Stellar 首先提供后者。

### 6.3 证据等级

| 等级 | 来源 | 界面含义 |
| --- | --- | --- |
| `verified` | 引擎元数据或已成功解析的当前 DDL | 可用于影响分析 |
| `partial` | DDL 只解析出部分引用 | 显示边与警告，不作完整性承诺 |
| `annotated` | 经权限控制的人工注释 | 明确标为人工维护，后续才支持 |
| `unknown` | 无法读取或无法解析 | 不画推测边，展示失败原因 |

LLM 不能产生 `verified` 关系，也不能把 `unknown` 升级为其他等级。

## 7. 分期与交付门槛

### 阶段 A：对象浏览器

**目标**：让用户在 SQL 工作台中快速确认一个真实对象的定义。

功能：

- 在现有对象树中点击表、View 或 MV 后打开只读对象详情。
- 展示对象类型、所属 Catalog / Database、字段、注释、原始 DDL 与读取时间。
- 对内部表展示解析成功的 Key Model、分区、分桶、引擎和属性；无法解析时只展示原始 DDL 与状态。
- 支持复制限定对象名、插入 SQL 编辑器、预览前 N 行和刷新当前对象。
- 刷新由后端生成受限的元数据读取命令，前端不提交任意 SQL。

阶段 A 不需要全库同步、图数据库或新顶层导航。它应替换当前由前端通过通用 SQL 执行接口读取 DDL 的路径。

Schema API 不返回数据样本。“预览前 N 行”仅将规范限定名写入现有 SQL 工作台；真正执行查询仍须经过已有的 SQL 执行权限、确认与限制。

**阶段 A 验收**：

1. 用户只能读取其组织内、具有对象浏览权限的集群对象。
2. UI 展示的对象身份、DDL 和字段来自同一次服务端读取，并显示读取时间。
3. 任意用户输入不能改变服务端生成的 SQL 语义；不存在的 Catalog、Database 或对象返回明确错误。
4. StarRocks / Doris 方言无法完整解析时，原始 DDL 完整可见，且页面不编造物理属性。
5. 用户可从对象详情回到 SQL 工作台并插入同一规范限定名。

### 阶段 B：局部依赖地图

**目标**：在真实对象详情中回答“它读取谁、谁读取它”。

功能：

- 从选中对象展开一跳上游与下游，默认上限为 50 个节点。
- 节点展示对象类型、对象名、最新成功采集时间和解析状态。
- 边展示 `view_reads`、`mv_reads` 或 `declared_constraint`，支持查看产生该边的 DDL 片段。
- 图按证据等级筛选；默认隐藏 `partial`，用户可显式打开。
- 解析失败、无权限读取或超出上限时显示原因和下一步，而非无提示截断。

阶段 B 的前提是用户访谈确认“依赖理解”确实是高频阻塞，并且目标集群的 View / MV DDL 解析覆盖足以形成有效地图。不能因为有画布组件就默认交付全库关系图。

### 阶段 C：DDL 快照与影响分析

**目标**：为受控变更提供事实基础，而非生成变更本身。

功能：

- 保存可追溯的对象 DDL 快照，包含集群、规范身份、采集时间、DDL 哈希和解析版本。
- 比较同一对象的两个快照，区分字段、键、分区、分桶、引擎、属性和对象类型变化。
- 根据 `verified` 依赖列出下游对象，并标注“已验证影响”或“需要人工确认”。
- 由授权用户手动触发同步和比较，过程与结果写入操作审计。

阶段 C 不做 DDL 自动提交、自动迁移和自动修复。Stellar 的现有审批与审计链路只接受明确、人工确认的运维动作。

## 8. 用户体验

### 8.1 入口

入口位于 SQL 工作台的 Catalog / Database / Table 树。对象右键菜单和详情动作保留“插入表名”“查询前 N 行”，新增“查看对象详情”。不新增“数据库设计”顶层菜单，避免将运行时事实浏览误解为建模能力。

物化视图列表的详情页可复用同一对象详情面板；当阶段 B 上线后，在详情中展示其上游对象和下游依赖入口。

### 8.2 对象详情

对象详情按以下顺序组织：

1. **摘要**：对象类型、规范路径、读取时间、解析状态、内部或外部对象标识。
2. **字段**：字段名、类型、可空、默认值、注释和可验证键标识。
3. **物理属性**：Key Model、分区、分桶、Engine 与重要 `PROPERTIES`。仅显示服务端解析出的字段。
4. **DDL**：只读代码视图、复制动作和原始 DDL。
5. **依赖**：阶段 B 后显示局部地图与证据清单。
6. **历史差异**：阶段 C 后显示快照选择和差异结果。

页面必须区分“读取失败”“未发现关系”“关系未解析”和“当前用户无权读取”。这些状态不能合并为一个空白面板。

### 8.3 影响分析的呈现

影响分析不使用“安全”或“无影响”这种绝对结论。它只输出：

- 已验证下游对象数量和列表。
- 无法读取或解析的对象数量。
- 本次比较覆盖的快照范围和时间。
- 需要人工确认的原因，例如外部 Catalog、DDL 解析失败或业务侧应用依赖未知。

## 9. 元数据与采集设计

### 9.1 单一事实来源

阶段 A 使用服务端按需读取；阶段 B、C 接入智能问数规划中的 MetadataSyncService。该服务是元数据的唯一写入者，Schema Explorer、智能问数和未来的影响分析均读取其结果。

不能创建独立的 `schema_*` 同步任务、重复保存同一份 DDL，或让图页面直接发起数据库扫描。

### 9.2 逻辑数据模型

以下为逻辑模型，不预先规定物理表名。具体迁移必须与智能问数元数据模型一并设计。

```text
SchemaSnapshot
  cluster_id, catalog, database, captured_at, collector_version,
  status, object_count, error_summary

SchemaObject
  identity, snapshot_id, object_kind, ddl_raw, ddl_hash,
  columns, physical_properties, parse_status, captured_at

SchemaDependency
  snapshot_id, source_identity, target_identity, relation_kind,
  evidence_level, evidence_excerpt, parser_version, captured_at
```

`ddl_raw` 是原始事实，`columns` 与 `physical_properties` 是可丢弃、可重建的解析派生数据。关系的 `evidence_excerpt` 只保存定位该关系所需的有限 DDL 片段，不保存业务数据行。

### 9.3 采集策略

- 阶段 A：按对象请求，服务端先验证对象可见性，再读取必要元数据。
- 阶段 B：按 Database 同步，先列对象，再按受限并发读取对象 DDL 并解析关系。
- 阶段 C：仅成功完成的同步产生可比较快照；失败或部分完成的同步不可被标记为完整基线。
- 大库必须设置对象数、DDL 大小、总耗时和并发上限。超出上限时输出 `partial` 状态和明确范围。
- 同一对象的同一 DDL 哈希不重复存储内容，只追加一次采集观察记录。保留策略在阶段 C 随审计和存储成本确定。

### 9.4 方言处理

StarRocks 与 Doris 均使用 MySQL 协议，但 DDL 语义不同。解析层按 `cluster_type` 与版本选择实现，不能把 MySQL 解析结果直接声明为完整语义。

对于未知语法：

1. 保留完整原始 DDL。
2. 将无法识别的段落标为未解析。
3. 不生成依赖边或物理属性推断。
4. 记录解析器版本和受限错误摘要，供后续兼容性改进。

## 10. API、权限与审计

### 10.1 API 边界

后端提供专用只读接口，而不是复用面向 SQL 工作台的通用执行接口。建议接口形态：

```text
GET  /api/clusters/:cluster_id/schema/objects
GET  /api/clusters/:cluster_id/schema/objects/:object_ref
POST /api/clusters/:cluster_id/schema/objects/:object_ref/refresh
GET  /api/clusters/:cluster_id/schema/objects/:object_ref/dependencies
GET  /api/clusters/:cluster_id/schema/snapshots                 # 阶段 C
GET  /api/clusters/:cluster_id/schema/diff                      # 阶段 C
```

`object_ref` 必须是服务端签发且绑定集群与规范对象身份的不透明引用，不能把未校验的对象名或 SQL 片段拼接进命令。后端按集群类型和对象类型生成固定的 `SHOW` / `information_schema` 查询，并参数化所有可参数化的值。

### 10.2 权限

建议新增独立的只读权限根 `schema`，至少包含：

```text
api:clusters:schema:list
api:clusters:schema:get
api:clusters:schema:refresh
api:clusters:schema:dependencies
api:clusters:schema:diff
```

所有请求必须：

1. 先验证目标集群属于当前组织，super admin 走明确的跨组织规则。
2. 再验证用户具备对应 API 权限。
3. 只使用服务端存储的集群连接与最小权限数据库账户。
4. 按对象、数据库与 Catalog 的引擎授权结果过滤响应。

### 10.3 审计

以下操作写入操作审计：手动刷新对象、批量同步、创建可比较快照、执行差异比较、导出完整 DDL 或影响清单。

普通只读查看沿用访问日志和必要的安全审计，不因每次展开字段都创建高噪声业务操作记录。

## 11. 安全与性能边界

- 浏览器只接收已授权的结构元数据，永不接收集群凭据、连接串或可复用会话信息。
- 不允许通过该功能执行 DDL、DML、管理命令或任意 SQL。
- Schema Explorer 的读取、解析和关系图不将 DDL、字段、依赖图或数据样本传给第三方分析、遥测或 LLM 服务。
- 对 DDL 响应、对象数、依赖深度、节点数、边数、查询超时和并发读取设置上限。
- 外部 Catalog 默认按引擎权限和组织策略处理；无权读取时仅返回受限状态，不泄露对象名称或 DDL。
- 依赖解析在服务端执行，解析器输入大小受限；异常必须隔离为单对象失败，不能阻断整个同步。

## 12. 与 DrawDB 的关系

DrawDB 可提供交互参考，例如局部表卡片、缩放定位和 SQL 导入后的结构概览；它不是 Stellar 的代码依赖或产品核心。

不直接集成的原因：

1. DrawDB 的自由编辑、浏览器本地存储和分享模型不以真实集群状态为事实来源。
2. 它不提供 StarRocks / Doris 的完整方言和物理语义。
3. 将其接入当前 Angular / Rust 单体会引入额外前端运行时、发布边界与许可证合规风险。

阶段 A 可提供“复制原始 DDL”作为低耦合互操作方式。任何导出到外部建模工具的行为都应标记为离线副本，不应回写 Stellar，更不能自动执行。

## 13. 验证与度量

### 13.1 用户研究

开发阶段 A 前，使用最近真实任务访谈至少覆盖 DBA / 运维、数仓工程师、分析工程师三类角色。每位用户应复盘一次以下任务之一：找表写 SQL、理解陌生表、修改 MV 或判断 DDL 影响。

访谈要记录用户当时使用的真实产物：SQL、`SHOW CREATE`、Wiki、截图或人工图，而不是询问“是否喜欢 ERD”。需要验证的假设是：用户是否因缺少可信结构信息而阻塞，而不是单纯希望看到一张图。

### 13.2 产品指标

阶段 A 记录：

- 从对象树进入详情后，复制限定名、插入 SQL、预览数据等后续动作比例。
- 结构读取成功率、读取延迟、解析成功率和方言失败分布。
- 用户从对象详情返回 SQL 工作台后执行查询的比例。

阶段 B 额外记录：

- 依赖地图的加载成功率、截断率与 `partial` 边占比。
- 用户从地图跳转到下游对象、MV 或 DDL 的比例。
- 抽样核验中被用户判定为错误或缺失的关系数。

阶段 C 额外记录：

- DDL 差异比较被用于审批或变更前检查的次数。
- 比较结果中的解析失败、权限不足和未知影响比例。

“打开图次数”不是成功指标；用户是否完成了找表、理解依赖或安全审查才是。

## 14. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| DDL 方言无法完整解析 | 产生错误属性或遗漏关系 | 原始 DDL 优先、部分解析标识、未知不推断 |
| 大库扫描过慢 | 影响 FE 或平台后端 | 按库同步、并发与大小上限、局部图 |
| 关系缺失 | 用户误以为无依赖 | 显示证据覆盖范围与未知状态，不声明完整血缘 |
| 结构元数据泄露 | 跨组织或跨权限暴露表定义 | 组织隔离、专用权限、服务端连接和对象过滤 |
| 与智能问数重复建设 | 数据漂移、维护成本增加 | MetadataSyncService 唯一写入者，统一逻辑模型 |
| 范围膨胀为建模工具 | 延误运维闭环 | 坚持只读事实、依赖证据和影响分析边界 |

## 15. 后续决策门

阶段 A 完成后，只有同时满足以下条件才进入阶段 B：

1. 用户研究和使用数据证明“理解依赖”是高频阻塞，而非“希望更好看地展示表”。
2. 目标集群的 View / MV DDL 能以可接受的覆盖率解析出可验证关系。
3. 图中的关系能够驱动明确后续动作，例如查看下游 MV、确认变更影响或回到 SQL 工作台。

阶段 B 完成后，只有真实变更审查反复需要比较历史定义时才进入阶段 C。

完整的可编辑数据建模功能是独立产品线。只有在多个目标团队持续证明其需要在 Stellar 内完成从零设计、协作评审和变更发布，且许可证与发布模型已单独审批后，才重新立项；它不属于本设计的自然延伸。
